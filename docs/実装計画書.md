## 1. 目的

本計画は、要件書で定義された初期版を、10〜20分のランとして最初から最後まで遊べる状態にするための実装順序と完了条件を定める。

MVPは単に機能一覧を実装した状態ではなく、次の体験が確認できた時点で完成とする。

1. ランごとに異なるビルドになる
2. 戦闘後の3択で悩める
3. ビルドによって戦闘方法が変わる
4. 戦闘中に前進・維持・後退の判断がある
5. 敗北またはクリア後に別構成で再挑戦したくなる

## 2. MVPスコープ

### 2.1 必須ゲームプレイ

- プレイヤー装甲車1台
- 横方向1画面の戦闘
- 前進、後退、位置維持
- 主武器、副武器、特殊能力
- 距離による武器性能と対応能力の変化
- 前線の押し引きとリスク・報酬
- 電力、熱、弾薬、耐久力
- 5種類以上の敵
- 6種類以上の武器
- 10種類以上のパーツ
- 複数Waveで構成される戦闘
- 戦闘後の3択報酬と装備変更
- Seedから再現可能な敵構成と報酬抽選
- 固定順の約10戦と最終ボス
- 勝利、敗北、ランリセット

### 2.2 必須プレゼンテーション

- プレイヤー、敵、武器の2Dレイヤー表示
- 装備中の武器・主要モジュールが車両外見へ反映される
- 固定された斜め横視点の2D Composition
- 地面と背景
- Projectile、Muzzle Flash、Hit、Explosion、Smoke、Overheatの最低限のVFX
- HP、Heat、Energy、Ammo、Wave、前線、武器状態を読めるHUD
- 報酬選択、装備変更、勝利、敗北、結果画面
- デバッグ表示

### 2.3 必須エンジニアリング

- 60Hz固定ステップのPure TypeScript Simulation
- React UI、Game Session、Simulation、Canvas 2D Presentationの分離
- データ駆動のWeapon、Module、Enemy、Wave、Reward、Boss定義
- Tag、Trigger / Condition / Effect、Modifier評価順
- `Math.random()`へ依存しないSeed付きRNG
- InputをPlayerCommandへ変換する境界
- Simulation EventをPresentationへ渡す境界
- ゲームルールの単体テストと固定Seedシナリオテスト
- コンテンツRegistryの整合性検証

### 2.4 MVP対象外

- 分岐ルートとマップ
- ショップ、修理地点、イベント
- キャラバン支援車両とキャラバン防衛
- 複数エリア
- 複数ボス
- 複雑な永続成長とアンロック
- 複数の初期車両・初期ビルド
- タッチ・ゲームパッド向けの完成UI
- 途中ランの保存・再開
- エンドレス、デイリー、チャレンジモード

対象外機能のための先回りした抽象化は行わない。ただし、SimulationとPresentationの分離やデータIDなど、MVPのテスト可能性に必要な境界は維持する。

## 3. MVPコンテンツ構成

### 3.1 武器6種類

| ID                | 役割                 | 主なTag                            | 距離による差別化             |
| ----------------- | -------------------- | ---------------------------------- | ---------------------------- |
| `machine_cannon`  | 標準的な連射武器     | ballistic, projectile              | 中距離で安定                 |
| `scatter_cannon`  | 複数弾の瞬間火力     | ballistic, projectile, close-range | 近距離ほど命中弾数が増える   |
| `flamethrower`    | 範囲・継続ダメージ   | fire, heat, close-range            | 至近距離専用                 |
| `rocket_launcher` | 範囲爆発             | explosive, projectile              | 中〜長距離、最低安全距離あり |
| `railgun`         | 高消費の精密貫通攻撃 | energy, long-range                 | 長距離で最大性能             |
| `mine_launcher`   | 後退時の空間制御     | explosive, deployable              | 敵を引きつけて使う           |

すべての武器を主武器・副武器のどちらへも装備できる。装備枠と重複規則は[ADR 0002](adr/0002-combat-loadout.md)で確定し、具体的な数値はフェーズ8まで調整対象とする。

### 3.2 パーツ10種類

| ID                   | 分類 | 戦い方への影響                           |
| -------------------- | ---- | ---------------------------------------- |
| `cooling_fan`        | 補助 | 熱を抑えて継続射撃しやすくする           |
| `generator`          | 補助 | 電力供給を増やす                         |
| `ammo_box`           | 補助 | 弾薬容量または補給方法を変える           |
| `armor`              | 防御 | 耐久または被ダメージ計算を変える         |
| `shield_generator`   | 防御 | 電力と引き換えに被害を防ぐ               |
| `radar`              | 補助 | 射程・命中・敵情報のいずれかを変える     |
| `heat_recycler`      | 特殊 | 高熱またはOverheatを電力へ変換する       |
| `capacitor`          | 特殊 | 電力枯渇をTriggerとして攻撃へ変換する    |
| `magnetic_armor`     | 特殊 | 敵弾を弾薬へ変換する機会を作る           |
| `explosive_magazine` | 特殊 | 爆発を強化する代わりに被弾リスクを増やす |

単純な数値上昇だけでなく、最低4種類はTrigger / Effectによって操作やリソース運用を変える。

### 3.3 敵5種類

| ID          | 役割               | 要求する判断           |
| ----------- | ------------------ | ---------------------- |
| `basic`     | 数で進行する標準敵 | 基本的な火力配分       |
| `rusher`    | 高速突破           | 優先撃破と後退         |
| `heavy`     | 高耐久・装甲       | 高火力武器と距離維持   |
| `artillery` | 遠距離攻撃         | 前進して射程へ入れる   |
| `bomber`    | 接近自爆           | 接近を許さない優先順位 |

Support / Shield / CommanderはMVP後の候補とする。必要な役割が不足した場合のみ、既存5種類のVariantとして検証する。

Presentationでは5種類を車両ではなく、苔・花角・瓦礫甲羅・胞子・爆裂果をモチーフにしたMonsterとして描く。ゲーム上のIDとBehaviorは維持する。

### 3.4 ボス1種類

`kawaii_fortress`を採用する。単なる高HP敵ではなく、砲撃、増援、弱点露出など複数の状態を持ち、距離管理・敵優先順位・ビルド運用を確認する最終試験にする。

### 3.5 ラン構成

- 戦闘1〜3: 基本操作と単一役割の敵
- 戦闘4〜6: 敵役割の組み合わせとリソース圧力
- 戦闘7〜9: 高密度Waveとビルドへの対策要求
- 戦闘10: ボス
- 各戦闘後: 3択報酬、装備変更、次戦闘開始

各戦闘のWaveはデータ定義し、SeedによるVariantで敵数・出現順・報酬候補を変える。戦闘数自体は固定し、ルート分岐は持たせない。

## 4. 実装アーキテクチャ

```text
React UI
  ↓ command / selection
Game Session
  ├─ Run phase
  ├─ Combat sequence
  ├─ Reward selection
  └─ Result / reset
  ↓
Simulation Core
  ├─ Movement / Distance / Frontline
  ├─ Combat / Projectile / Damage
  ├─ Resources / Status
  ├─ Weapon / Trigger / Modifier
  ├─ Enemy Behavior / Wave / Boss
  └─ Seeded RNG

Canvas 2D Presentation
  └─ Simulation Snapshot / Combat Eventを読む
```

### 4.1 状態の所有者

- `RunState`: seed、戦闘番号、獲得装備、ビルド、結果
- `CombatState`: player、enemy、projectile、wave、frontline、resources
- `BuildState`: weapon slot、module、tag、modifier、runtime effect
- `UIState`: 開いている画面、選択、tooltip、modal

UIStateはSimulationへ含めず、Canvas描画オブジェクトもゲーム状態へ含めない。

### 4.2 データと実装の境界

- 数値・Tag・Asset ID・Behavior IDはDefinitionに置く
- 通常挙動はSystemで処理する
- 特殊な敵挙動だけをBehavior Registryへ実装する
- パーツ効果は可能な限りTrigger / Condition / Effectで表す
- 複雑な効果を無理に汎用DSLへ押し込まず、必要時は型付きEffect実装を追加する

### 4.3 決定論

同一のゲームバージョンにおいて、`seed + 初期構成 + PlayerCommand列`から同じSimulation結果を得られることを目標とする。

- RNGはRun単位で所有する
- 乱数消費箇所をReward、Wave Variantなど用途別に分離する
- Entity処理順を安定させる
- Presentationは乱数を使用してよいがSimulationへ結果を戻さない
- 主要シナリオは固定Seedの回帰テストを持つ

## 7. テスト方針

### 7.1 単体テスト

- Movement、Distance、Collision、Damage
- Weapon cooldown、Projectile、Ammo、Heat、Energy
- Modifier評価順
- Triggerの条件、順序、連鎖制限
- RNGの再現性と用途別stream
- Enemy Behavior、Wave、Victory / Defeat
- Reward候補とBuild反映
- Run reset

### 7.2 シナリオテスト

固定Seed、固定Build、固定Command列を使い、一定tick後のEnemy数、HP、Heat、Energy、Ammo、Damage、phaseを検証する。

最低限、次のBuildを回帰対象にする。

- 標準機関砲
- 近距離火炎・冷却
- 長距離Railgun・Generator
- Rocket・Explosive Magazine
- Ammo / Energy枯渇Trigger

### 7.3 コンテンツ検証

- ID重複なし
- 参照先Definition・Behavior・Assetが存在する
- 必須Tagと表示文がある
- 武器6、パーツ10、敵5、ボス1、戦闘10を満たす
- Reward poolから取得不能な装備がない

### 7.4 手動プレイテスト

各テストでSeed、最終Build、選択に迷った回数、主な敗因、前進・後退の理由、再挑戦意向を記録する。単なるクリア率だけで判断しない。

## 9. コミット方針

各フェーズを一つの巨大コミットにはしない。次の単位を目安に、常に検証可能な状態でコミットする。

- Simulationの型・規則とそのテスト
- データDefinitionとRegistry検証
- Game Sessionのphase単位
- React UIの画面単位
- Canvas 2D ViewまたはAsset群単位
- バランス値変更は、機能変更と可能な限り分離
- 文書で確定した仕様変更

各コミット前に原則として`npm run check`を実行する。視覚変更では開発サーバー上の表示も確認する。

## 10. MVP完了のDefinition of Done

次のすべてを満たしたとき、MVPを完了とする。

- トレーサビリティ表のMVP-01〜18、CORE-01〜04、PRES-01が完了している
- 必須コンテンツ数と全参照を自動検証できる
- 固定Seedシナリオテストが再現可能である
- 実アセットを用いた10戦のランを開始から結果まで遊べる
- 勝利と敗北の双方から新しいランへ戻れる
- `npm run check`が成功する
- 重大な進行不能、操作不能、視認不能がない
- 10〜20分の目標時間に収まる
- 5つの体験合格条件をプレイテストで満たす
