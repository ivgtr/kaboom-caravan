# ローグライク装甲車キャラバン 技術設計書

## 1. 技術設計方針

本ゲームはWebブラウザ上で動作する、横方向戦闘を中心とした2.5Dローグライクゲームとして設計する。

技術設計では以下を最優先する。

1. ゲームロジックと描画を分離する
2. 3D表現を採用するが、ゲームルール自体は3D空間に依存させない
3. ビルド・シナジー追加を容易にする
4. 敵・武器・パーツをデータ駆動で増やせるようにする
5. MVP段階で不要な汎用化を行わない
6. ゲームループを決定論的に扱える構造にする
7. 大量の敵・弾・エフェクトが存在しても安定して描画できる構造にする

---

# 2. 採用技術

| 用途 | 採用 |
|---|---|
| 言語 | TypeScript |
| 開発環境 | Vite |
| 3D描画 | Three.js |
| UI | React |
| 3Dアセット | glTF / GLB |
| 音声 | Web Audio API |
| 単体テスト | Vitest |
| ブラウザテスト | Playwright |
| 物理エンジン | 初期版では使用しない |

Three.jsはWeb向け3DライブラリとしてScene、Camera、Material、Light、Textureなどの描画基盤を提供する。現在はWebGLとWebGPUの双方に対応している。

ただし初期版では互換性と予測可能性を優先し、**WebGLRendererを標準描画経路**とする。

WebGPUは将来的な描画最適化候補とし、ゲームロジックが特定レンダラーへ依存しない構造を維持する。

---

# 3. 2.5D構成

ゲームは3Dモデルを使用するが、ゲームルール上の戦闘空間は限定する。

概念上は以下の構造とする。

```text
Three.js World

          背景
           │
敵 ───────────── 装甲車
           │
         地面

      ← ゲーム進行方向 →
```

ゲームロジックで重要なのは基本的に、

- 横方向位置
- 高さ
- 距離
- 速度

のみとする。

奥行き方向は主として、

- モデル表示
- 地形
- 背景
- パーティクル
- カメラ演出
- 敵の見た目上のばらつき

に利用する。

つまり、

```text
Simulation
x / y

↓

Presentation

x / y / z
```

という変換を行う。

---

# 4. カメラ

基本カメラには固定された斜め横視点を使用する。

完全な真横ではなく、車両の、

- 車体
- 車輪
- 武器
- 装甲
- 支援装備

が立体的に確認できる程度に角度をつける。

基本的にはOrthographic Cameraを第一候補とする。

理由は、

- 敵との距離が視覚的に分かりやすい
- 遠近によるサイズ差が発生しない
- 前線位置を把握しやすい
- ゲームプレイ上の座標と画面位置が安定する

ため。

演出時のみ、

- Zoom
- Shake
- Look Ahead
- Slow Motion

などを加える。

---

# 5. アーキテクチャ

ゲーム全体を大きく4層へ分離する。

```text
┌────────────────────────┐
│          UI            │
│        React           │
└──────────┬─────────────┘
           │ Snapshot
┌──────────▼─────────────┐
│      Game Session      │
│ Run / Phase / Reward   │
└──────────┬─────────────┘
           │
┌──────────▼─────────────┐
│    Simulation Core     │
│ Combat / Build / RNG   │
└──────────┬─────────────┘
           │ Presentation State
┌──────────▼─────────────┐
│     Presentation       │
│      Three.js          │
└────────────────────────┘
```

依存方向は必ず、

```text
UI
 ↓
Session
 ↓
Simulation

Presentation
 ↓
Simulationの結果を読む
```

とする。

Three.jsオブジェクトからGameStateを直接変更することは禁止する。

# 6. Simulation Core

ゲームの中心。

Three.js、React、DOMなどに依存しない純粋なTypeScriptとして実装する。

主な責務は、

- プレイヤー移動
- 敵移動
- 武器処理
- Projectile処理
- Damage処理
- Wave進行
- 距離判定
- Heat
- Energy
- Ammo
- Status Effect
- Trigger
- Victory / Defeat

とする。

---

# 7. 固定タイムステップ

ゲームロジックは描画FPSから分離する。

例えば、

```text
Simulation
60 step / sec

Rendering
30〜120 FPS
```

として扱う。

ゲーム更新は固定時間で処理する。

これにより、

- 高リフレッシュレート環境
- 低FPS環境
- テスト
- リプレイ
- バランス検証

で同じ結果を得やすくする。

描画側は前後のSimulation状態を補間して表示する。

---

# 8. Game Entity

ゲーム内オブジェクトはThree.jsのMeshそのものをEntityとして扱わない。

例えば敵は、

```text
Enemy
├─ id
├─ type
├─ position
├─ velocity
├─ hp
├─ status
└─ behavior
```

というゲーム上のEntityを持つ。

Three.js側では、

```text
EnemyVisual
└─ Object3D
```

として対応付ける。

つまり、

```text
Enemy Entity
        ↓
EnemyVisual
        ↓
Three.Object3D
```

となる。

Enemy Entityが死亡すればEnemyVisualを破棄する。

# 9. ECSについて

本格的なECSライブラリは初期段階では導入しない。

ただし設計思想として、

```text
Entity
+
Component的な状態
+
System
```

の分離は行う。

例えば、

```text
Enemy

Position
Health
Movement
Combat
Status
```

をSystemが処理する。

MVP段階ではTypeScriptの型とMap/Arrayを利用した軽量構造で十分とする。

ゲーム規模が大きくなってから必要性を再評価する。

# 10. 戦闘座標

戦闘フィールドにはゲーム専用座標を使用する。

例えば、

```text
PLAYER_BASE = 0

敵陣
100 ────────────────── 0
                         ↑
                       自陣
```

のような単純な数値空間とする。

Three.jsのworld座標を直接ゲームルールへ利用しない。

これにより、

- カメラ変更
- モデルサイズ変更
- 演出
- スケール変更

がゲームバランスへ影響しない。

---

# 11. Collision

初期版では物理エンジンを利用しない。

敵やProjectileのCollisionは、

- Range
- Circle
- AABB
- Line Segment

など単純な数学的判定で実装する。

例えば砲弾なら、

```text
previousPosition
      │
      └──────── newPosition

この区間とEnemy Colliderの交差を判定
```

する。

本ゲームの主なCollisionは、

- Projectile → Enemy
- Enemy → Player
- Area Attack
- Explosion
- Mine
- Melee Range

程度であり、物理シミュレーションを必要としない。

---

# 12. 物理エンジンの扱い

Rapierは2D/3D双方に対応し、

- Rigid Body
- Collision
- Joint
- Ray Cast
- Sensor

などを提供する。

ただし初期版では採用しない。

将来的に、

- 車両サスペンション
- 破片
- 瓦礫
- 物理オブジェクト
- 車両同士の衝突

などがゲームプレイ上重要になった場合のみ導入を検討する。

その場合でも、

**ゲーム判定用Physicsと演出用Physicsを可能な限り分離する。**

# 14. Weapon System

Weaponはデータ定義と動作実装を分離する。

WeaponDefinitionは、

- ID
- 表示名
- 攻撃方式
- Damage
- Cooldown
- Range
- Ammo Cost
- Energy Cost
- Heat
- Projectile
- Tags

を持つ。

例：

```text
flamethrower

tags:
  fire
  close-range
  heat
```

ゲーム中のシナジー判定ではIDそのものではなくTagを積極的に利用する。

# 15. Tags

シナジー構築の基盤としてTagシステムを導入する。

例：

```text
fire
explosive
projectile
energy
ballistic
drone
heat
shield
close-range
long-range
```

例えば、

> 爆発武器のDamage +30%

という装備は、

```text
explosive
```

Tagを持つWeaponへ作用する。

これにより新武器追加時に既存パーツへ個別対応を追加する必要を減らす。

# 16. Trigger / Effect System

本ゲームのビルドシステムで最重要となる基盤。

特殊パーツは、

```text
Trigger
↓
Condition
↓
Effect
```

として表現する。

例：

```text
Trigger
ammo-empty

Condition
weapon.tag == explosive

Effect
reload
fire
damage-bonus
```

主要Trigger候補：

- onFire
- onHit
- onKill
- onCritical
- onDamage
- onAmmoEmpty
- onEnergyEmpty
- onOverheat
- onCooldownReady
- onEnemyEnterRange
- onEnemyLeaveRange
- onWaveStart
- onWaveEnd

これによって、

> 弾薬が0になった瞬間に全武器を再発射

のような特殊効果を、巨大な条件分岐へ追加せず実装できる構造とする。

以下はデータ定義として管理する。

- Weapons
- Modules
- Enemies
- Waves
- Rewards
- Vehicles
- Bosses
- Status Effects

例えばEnemyDefinitionは、

```text

```

# 19. Behavior

すべてをデータだけで表現しようとはしない。

特殊な挙動にはBehavior実装を使用する。

例：

```text
normalAdvance
rush
stopAndShoot
shieldSupport
suicideRush
bossPhase
```

データ側では、

```text
behavior: "rush"
```

として参照する。

Behavior Registryから実装を取得する。

これにより、

「完全データ駆動による複雑化」

も避ける。

# 20. RNG

ローグライク部分にはSeed付き疑似乱数を使用する。

対象：

- Route
- Reward
- Shop
- Wave Variant
- Event
- Loot

など。

Simulation Coreでは直接 `Math.random()` を使用しない。

これによって、

```text

+
Player Input
=
同じ結果
```

に近づける。

バグ再現やバランス検証にも利用する。

# 23. モジュール装備の表示

武器交換とModule取得が2D車体の外見にも反映されるようにする。

車体Spriteには中央X・Ground Yを原点とするAttachment Pointを用意する。

例：

```text
Caravan Sprite
├─ weapon_main
├─ weapon_sub
├─ module_rear_0
├─ module_rear_1
├─ module_rear_2
├─ module_roof_0
├─ effect_exhaust
└─ effect_muzzle
```

標準BatteryとRear Railは車体Spriteへ統合する。取得ModuleはBuildの`moduleIds`順に4つのAttachment Pointへ割り当てる。描画順はConnector／Cradle、Module画像、前面Retainer／Boltとし、画像を裸で車体へ重ねない。Module画像は元のAspect Ratioを維持する。

これにより、

> ビルドが外見として成長する

状態を作る。

# 26. 敵描画

敵数が少ない段階では通常Meshを使用する。

敵数が増加した場合は、

- Object Pool
- InstancedMesh

を段階的に導入する。

Three.jsのInstancedMeshは同一Geometry/Materialのオブジェクトをまとめて描画し、Draw Callを減らす目的で利用できる。

想定：

```text
BasicEnemy
× 50

↓

InstancedMesh
1 draw group
```

ただしMVPから無条件にInstancingを導入しない。

実測して必要になった時点で採用する。

# 29. UI

HUD・メニュー・報酬画面・装備画面などはReactで実装する。

Three.js Canvasの上へDOMとして重ねる。

```text
┌────────────────────────────┐
│ React HUD                  │
│ HP Heat Energy Ammo        │
│                            │
│      Three.js Canvas       │
│                            │
│                   Skill UI │
└────────────────────────────┘
```

3D Scene内へUIを配置しない。

理由：

- テキスト品質
- レスポンシブ
- アクセシビリティ
- 操作
- レイアウト

をDOMへ任せるため。

# 30. React Three Fiber

React Three Fiberは採用しない。

React Three FiberはReact向けThree.js Rendererであり、React 19にも対応している。

しかし本ゲームでは、

- 固定Simulation Loop
- 大量Entity
- Object Pool
- Imperative Animation
- Scene lifecycle

がゲームの中心になる。

そのため、

```text
React
→ UI

Three.js
→ Game Rendering
```

と責務を明確に分ける。

ReactからThree.js Scene Graphを直接管理しない。

# 32. Reactとの同期

Simulationの全状態を毎Frame Reactへ流さない。

Reactへ必要なSnapshotのみ公開する。

例えば、

```text
60fps Simulation

↓

UI Snapshot 10〜20fps
または
値変更時のみ通知

↓

React
```

とする。

HPや弾薬などはSnapshotとしてUIへ伝える。

敵の位置など描画専用データはReactへ渡さない。

---

# 33. Input

入力を直接Game Logicへ接続しない。

```text
Keyboard
Pointer
Touch
Gamepad
   ↓
InputManager
   ↓
PlayerCommand
   ↓
Simulation
```

PlayerCommand例：

```text
move
firePrimary
fireSecondary
activateSkill
```

`move`は位置へ直接加算せず、Playerの目標速度として扱う。SimulationはPlayerStateへ
`velocity`を保持し、加速、惰性減速、逆入力時の制動をFixed Stepで計算する。
描画はこの速度と実移動距離からHub Marker回転と排気Smokeを求める。車体と車輪の接地は固定する。

これにより将来、

- Keyboard
- Controller
- Touch

を同じGame Logicへ接続できる。

# 46. 採用しない構成

## Phaser中心構成

PhaserはWeb向けゲームフレームワークとして成熟しているが、公式にも2Dゲームフレームワークと位置付けられている。

今回の3D装甲車表現を中心とする場合は採用しない。

## PixiJS中心構成

PixiJSは高速な2Dレンダラーで、WebGL/WebGPUに対応する。

2Dスプライトゲームであれば有力だが、今回の車体・砲塔・パーツ交換を立体表現する目的ではThree.jsを優先する。

## Babylon.js

Babylon.jsは、

- WebGL
- WebGPU
- Physics
- Animation
- Particle
- Audio
- GUI

まで含む総合的な3D Engineである。

本ゲームでも実現可能だが、今回は必要なゲームルールを独自Simulationとして持つため、より薄い描画ライブラリであるThree.jsを採用する。

## React Three Fiber

Three.js SceneをReact Component Treeへ統合しない。

## 3D Physics中心設計

採用しない。

横方向戦闘というゲーム性に対して過剰な複雑性となるため。

```text
Vite
+

+

+

```

とする。

# 48. 技術設計上の最重要原則

Three.jsはゲームそのものではなく、

**ゲーム状態を魅力的に可視化するRendererとして扱う。**

ゲームの本質である、

- ビルド
- シナジー
- 距離管理
- 前線
- 敵AI
- Wave
- Damage
- Resources

はすべてThree.jsから独立させる。

これにより、

> 見た目は3Dだが、ゲームロジックは単純で検証可能

という構造を維持する。

これを本プロジェクトの技術設計における最上位原則とする。
